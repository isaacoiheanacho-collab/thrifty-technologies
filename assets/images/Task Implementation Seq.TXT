Phase B — Auth pages (in dependency order)
TASK 3 — frontend/auth/register.html (new)
Purpose: Saver registration via branch landing. Reads ?branch=<slug>, collects full name / phone / password, posts to POST /api/auth/register with branchSlug and the two consent objects.

Depends on: TASK 1, TASK 2.

Verify: Open http://localhost:3000/auth/register.html?branch=<real-slug>. Fill and submit. Expect 201 with { userId }, then auto-redirect to verify.html.

TASK 4 — frontend/auth/verify.html (new)
Purpose: OTP entry. Reads ?phone=<phone> and ?next=<path>. Posts to POST /api/auth/verify-phone. On success, stores tokens, redirects to next (or role-appropriate dashboard).

Depends on: TASK 1, TASK 2, TASK 3 (in the sense that register.html links here).

Verify: Register a fresh user, land on verify, enter the DEV OTP (the one logged in the server console in dev mode), expect 200, expect token storage in localStorage, expect redirect to /saver/dashboard.html (which will 404 — that's expected; next task fixes it).

TASK 5 — frontend/auth/forgot-password.html (new)
Purpose: Two-step password reset. Step 1: enter phone → POST /api/auth/password/forgot. Step 2: enter OTP + new password → POST /api/auth/password/reset.

Depends on: TASK 1, TASK 2.

Verify: Full flow with a real account on the backend.

Rule for the rest of this project
For every task, the workflow is:

I deliver the full file (or full new file) with no patches.

You save it.

You run the specific verification for that task.

You paste the verification output.

Only then do we move to the next task.

No task assumes a file is correct until it's been verified. No task depends on a file that hasn't been verified. No guessing about backend routes — TASK 0 gives us ground truth first.
